# ADR 002: پردازش سفارش‌ها در پس‌زمینه، Retry و DLQ

## وضعیت

پذیرفته‌شده — پیاده‌سازی اولیه.

## زمینه

سرویس باید بعد از پذیرفته‌شدن سفارش توسط API، آن را به‌صورت غیرهم‌زمان پردازش کند. همچنین، در صورت شکست پردازش، باید امکان ثبت خطا، تلاش مجدد و انتقال سفارش به وضعیت Dead Letter وجود داشته باشد.

در پیاده‌سازی فعلی از SQL Server استفاده می‌شود و هیچ Message Broker خارجی به پروژه اضافه نشده است.

## تصمیم

سفارش‌ها در جدول `Orders` ذخیره می‌شوند و وضعیت اولیه‌ی آن‌ها `Pending` است.

یک `BackgroundService` با نام `OrderProcessingService` به‌صورت دوره‌ای سفارش‌های دارای وضعیت `Pending` را از SQL Server دریافت می‌کند.

روند پردازش به این صورت است:

1. قدیمی‌ترین سفارش با وضعیت `Pending` انتخاب می‌شود.
2. عملیات پردازش سفارش اجرا می‌شود.
3. در صورت موفقیت، وضعیت سفارش به `Processed` تغییر می‌کند و مقدار `LastError` پاک می‌شود.
4. در صورت شکست، مقدار `RetryCount` افزایش می‌یابد و پیام خطا در `LastError` ذخیره می‌شود.
5. پس از سه تلاش ناموفق، وضعیت سفارش به `DeadLetter` تغییر می‌کند.
6. سفارش‌های دارای وضعیت `DeadLetter` توسط Worker فعلی دوباره انتخاب نمی‌شوند.

Worker تقریباً هر پنج ثانیه یک‌بار سفارش‌ها را بررسی می‌کند. حداکثر تعداد تلاش‌های ناموفق برای هر سفارش سه بار است.

## گزینه‌های بررسی‌شده

### استفاده از Message Broker خارجی

ابزارهایی مانند RabbitMQ یا Azure Service Bus امکانات پیشرفته‌تری برای انتقال پیام، مدیریت Retry و پردازش پیام‌های ناموفق ارائه می‌دهند.

در پیاده‌سازی اولیه، برای ساده نگه‌داشتن پروژه و استفاده از زیرساخت موجود، تصمیم گرفته شد که وضعیت سفارش‌ها در SQL Server نگهداری شود و از Message Broker خارجی استفاده نشود.

### پردازش هم‌زمان با درخواست API

در این روش، پردازش سفارش مستقیماً هنگام دریافت درخواست API انجام می‌شود. در نتیجه، پاسخ API به مدت زمان پردازش وابسته خواهد بود.

برای جداکردن زمان پاسخ API از زمان پردازش سفارش، روش پردازش غیرهم‌زمان انتخاب شد.

## پیامدهای تصمیم

### مزایا

- وضعیت سفارش‌ها در SQL Server ذخیره می‌شود.
- API می‌تواند سفارش را پیش از پایان پردازش بپذیرد.
- وضعیت پردازش و اطلاعات خطا از طریق دیتابیس قابل بررسی است.
- پس از سه تلاش ناموفق، سفارش به وضعیت `DeadLetter` منتقل می‌شود.
- برای پیاده‌سازی فعلی نیازی به Message Broker خارجی نیست.

### محدودیت‌ها

- منطق واقعی پردازش سفارش هنوز پیاده‌سازی نشده و بخش پردازش فعلی یک Placeholder است.
- رفتار Retry و DLQ با استفاده از یک خطای شبیه‌سازی‌شده آزمایش شده است.
- `Exponential Backoff` پیاده‌سازی نشده است؛ تلاش‌های مجدد به فاصله‌ی زمانی Polling وابسته‌اند.
- برای جلوگیری از پردازش هم‌زمان یک سفارش توسط چند Worker، مکانیزم Claim، Locking یا هماهنگی بین Instanceها وجود ندارد.
- اگر خطایی قبل از ذخیره‌شدن اطلاعات Retry رخ دهد، ممکن است تلاش ناموفق در دیتابیس ثبت نشود.
- مکانیزم خودکار برای بررسی یا پردازش مجدد سفارش‌های `DeadLetter` وجود ندارد.

## اعتبارسنجی

پروژه با موفقیت Build و اجرا شده است. برای بررسی رفتار Retry و DLQ، یک خطای شبیه‌سازی‌شده ایجاد شد. نتیجه نشان داد که پس از سه تلاش ناموفق، مقدار `RetryCount` به سه می‌رسد و وضعیت سفارش به `DeadLetter` تغییر می‌کند.

تست خودکار Concurrency و تست چند Worker هنوز پیاده‌سازی نشده‌اند.
