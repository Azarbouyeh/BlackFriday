# Black Friday Sale Reservation Service

## 1. معرفی پروژه

این پروژه یک REST API برای مدیریت رویدادهای فروش ویژه و رزرو موجودی محصولات با پشتیبانی از Multi-Tenancy است. هدف اصلی، جلوگیری از Overselling و اطمینان از جداسازی داده‌های Tenantها است.

**فناوری‌های استفاده‌شده:**
- C#
- ASP.NET Core Web API
- Entity Framework Core
- SQL Server
- Swagger / OpenAPI
- BackgroundService

## 2. قابلیت‌های پیاده‌سازی‌شده

- دریافت رویدادهای فروش بر اساس `TenantId`.
- ایجاد رزرو برای رویداد فروش فعال.
- کاهش اتمیک موجودی با استفاده از شرط در دستور SQL.
- استفاده از Database Transaction برای کاهش موجودی و ثبت رزرو.
- جلوگیری از رزرو در صورت اتمام موجودی، غیرفعال بودن رویداد یا عدم تطابق Tenant.
- ایجاد داده‌های اولیه برای دو Tenant شامل رویدادهای فعال، آینده و منقضی‌شده.
- ذخیره‌ی سفارش‌ها در SQL Server با استفاده از مدل `Order`.
- پردازش پس‌زمینه‌ی سفارش‌های دارای وضعیت `Pending` با استفاده از `BackgroundService`.
- تغییر وضعیت سفارش موفق به `Processed`.
- افزایش `RetryCount` و ذخیره‌ی خطا در `LastError` هنگام شکست پردازش.
- انتقال سفارش به وضعیت `DeadLetter` پس از سه تلاش ناموفق.

## 3. API Endpoints

### دریافت رویدادهای فروش

`GET /api/tenants/{tenantId}/sale-events`

فهرست رویدادهای فروش مربوط به Tenant مشخص‌شده را برمی‌گرداند.

### ایجاد رزرو

`POST /api/tenants/{tenantId}/reservations`

نمونه‌ی درخواست:

```json
{
  "saleEventId": 1
}
```

در صورت موفقیت، اطلاعات رزرو ایجادشده برگردانده می‌شود. اگر رویداد قابل رزرو نباشد، موجودی کافی نباشد یا رویداد متعلق به Tenant دیگری باشد، پاسخ `409 Conflict` داده می‌شود.

### ایجاد سفارش

`POST /api/tenants/{tenantId}/orders`

نمونه‌ی درخواست:

```json
{
  "reservationId": 1
}
```

در صورت پذیرفته‌شدن درخواست، پاسخ `202 Accepted` برگردانده می‌شود و سفارش با وضعیت `Pending` ذخیره می‌شود. سپس BackgroundService آن را برای پردازش انتخاب می‌کند.

در پیاده‌سازی فعلی، Endpoint فقط مثبت‌بودن `ReservationId` را بررسی می‌کند؛ وجود واقعی رزرو و تعلق آن به همان Tenant هنوز اعتبارسنجی نمی‌شود.

## 4. تصمیم معماری: جلوگیری از Overselling

کاهش موجودی با یک دستور شرطی SQL انجام می‌شود که فقط زمانی موجودی را کاهش می‌دهد که:

- شناسه‌ی رویداد و Tenant مطابقت داشته باشند.
- موجودی بیشتر از صفر باشد.
- رویداد در بازه‌ی زمانی فعال قرار داشته باشد.

سپس ثبت رزرو و کاهش موجودی در یک Database Transaction انجام می‌شوند. این روش به جلوگیری از رزرو بیش از موجودی در درخواست‌های هم‌زمان کمک می‌کند.

## 5. پردازش سفارش‌ها، Retry و DLQ

سفارش‌ها در جدول `Orders` ذخیره می‌شوند و در ابتدا وضعیت `Pending` دارند.

یک `BackgroundService` به‌صورت دوره‌ای سفارش‌های Pending را از SQL Server می‌خواند و پردازش می‌کند.

- در صورت موفقیت، وضعیت سفارش به `Processed` تغییر می‌کند.
- در صورت شکست پردازش، مقدار `RetryCount` افزایش می‌یابد و خطا در `LastError` ذخیره می‌شود.
- پس از سه تلاش ناموفق، وضعیت سفارش به `DeadLetter` تغییر می‌کند.
- سفارش‌های `DeadLetter` دیگر توسط Worker فعلی به‌صورت خودکار انتخاب نمی‌شوند.

**محدودیت‌های فعلی این بخش:**

- عملیات واقعی پردازش سفارش هنوز پیاده‌سازی نشده و بخش پردازش یک Placeholder است.
- رفتار Retry و DLQ با یک خطای شبیه‌سازی‌شده آزمایش شده است.
- Retry با تأخیر افزایشی (Exponential Backoff) پیاده‌سازی نشده است.
- هماهنگی بین چند Worker یا چند instance برای جلوگیری از پردازش هم‌زمان یک سفارش پیاده‌سازی نشده است.

## 6. اجرای محلی

1. اجرای SQL Server.
2. تنظیم `DefaultConnection` در `appsettings.json`.
3. اعمال Migrationهای Entity Framework Core روی دیتابیس.
4. اجرای پروژه در Visual Studio.
5. استفاده از Swagger برای مشاهده و تست Endpointها.

## 7. وضعیت اعتبارسنجی

موارد زیر به‌صورت دستی آزمایش شده‌اند:

- اجرای موفق پروژه و Build.
- دریافت فهرست رویدادهای فروش از طریق Swagger.
- ایجاد رزرو موفق با پاسخ HTTP 200.
- کاهش موجودی پس از ایجاد رزرو.
- رد درخواست رزرو با Tenant نامنطبق با پاسخ HTTP 409.
- ایجاد سفارش از طریق Orders API.
- پردازش موفق سفارش و تغییر وضعیت آن به `Processed`.
- شبیه‌سازی شکست پردازش و بررسی افزایش `RetryCount`.
- انتقال سفارش به `DeadLetter` پس از سه تلاش ناموفق.
- بررسی وضعیت سفارش و خطای ذخیره‌شده در SQL Server.

تست خودکار Concurrency یا تست بار اجرا نشده است.

## 8. محدودیت‌ها و کارهای باقی‌مانده

- تست خودکار یا اسکریپت اختصاصی برای بررسی درخواست‌های هم‌زمان هنوز پیاده‌سازی نشده است.
- عملیات واقعی پردازش سفارش باید جایگزین Placeholder شود.
- اعتبارسنجی وجود رزرو و Tenant مالک آن در Orders API باید اضافه شود.
- Retry با Exponential Backoff و هماهنگی چند Worker هنوز پیاده‌سازی نشده است.
- Docker Compose برای اجرای SQL Server آماده نشده است.
- ارتقا به .NET 8 یا بالاتر هنوز انجام نشده است.
- استراتژی بهینه‌سازی خواندن و تصمیم‌های مربوط به Cache، Consistency و Staleness هنوز کامل نشده‌اند.
